# Proposal: Track Catalog and Persistent Playlists

## Why

The current playlist concept is a minimal in-memory structure (`Playlist(id, name, trackIds)`) that resets on every restart, is read-only to clients, and cannot represent anything beyond file-backed tracks discovered by the local library scan. The upstream desktop application (being replaced) demonstrates that a richer model — where tracks are self-describing entities carrying their own metadata, state, and source information — enables stream-source integrations (e.g. Bandcamp), playlist persistence, and dramatically simpler clients that never touch tag-parsing libraries. We need that model on the server before any stream integration, playlist editing, or client-side metadata correction workflow can exist.

## What Changes

- **Unified track registry** (**BREAKING**): the media catalog becomes the single metadata-bearing registry for *all* tracks — file-backed and stream-backed — discriminated by `kind` (`FILE` | `STREAM`). Track identity is derived for all kinds: `sha1` of the relative path for files, `sha1` of the normalized source URL (volatile query params stripped) for streams — no random IDs. Tracks carry multi-value metadata (well-known keys such as `ARTIST`, `ALBUM`, `TITLE`, `ALBUM_ARTIST`, `DATE`, `TRACK`, `TRACK_TOTAL`, plus open custom keys), first-class duration, per-track state (`failing`, structured last-error with kind/message/timestamp/reporter), and source information. Stream tracks additionally carry `sourceUrl` (stable), `streamUrl` (volatile), and `expiresAfter`.
- **Scan reconciliation with reference-scoped tombstones** (**BREAKING**): startup scan extracts full metadata (not just duration) from audio files and snapshots it into registry tracks. Rescan reconciles: refreshes metadata and state for known tracks, creates tracks for new files, and for missing files tombstones the track (`SOURCE_MISSING`) only when at least one playlist references it — unreferenced tracks are removed outright.
- **Persistent playlists** (**BREAKING**): playlists become durable, mutable entities stored server-side. A playlist is a named, ordered list of track references (borrowed by identity — tracks are shared, never copied). Per-track state and metadata edits are therefore naturally visible in every playlist referencing that track. Playlists survive server restarts. There is no default playlist: catalog browsing is served by the track listing endpoint, and a client may explicitly materialize the full registry into an ordinary persisted playlist on demand.
- **Playlist mutation API** (**BREAKING**): clients can create playlists from registry tracks, from stream source URLs (one URL may resolve to many tracks — list-in/list-out), or by materializing the full registry; reorder/remove entries; and edit track metadata. Metadata edits are server-owned and fan out to all playlists via shared track identity. Tag write-back to source files is behind a handler SPI with a no-op implementation for now (read-only library); real write-back is a separate future capability.
- **Persistent playback state** (**BREAKING**): playback context (active playlist, current track, transport state, position with origin) is stored in the database keyed by `session_id` (`default` row until user sessions exist). Playback mode moves from global to per-playlist (new playlists default to `SEQUENTIAL`; user alterations are remembered). Transport state is persisted truthfully, but the server normalizes `PLAYING` → `PAUSED` on server restart and on client init/connect requests.
- **Audio streaming resolution** (**BREAKING**): `GET /api/stream/{trackId}` becomes source-aware. File tracks stream from disk as today; stream tracks are proxied through the server from their `streamUrl`, hiding integration details from clients. When a stream URL is missing or expired, the server refreshes it via a stream resolver SPI before serving.
- **Preemptive stream refresh**: a configurable scheduler refreshes stream URLs ahead of expiry (default: within one hour of `expiresAfter`), scoped to the active playlist plus a next-track check, to avoid abusing third-party services. In-request refresh at stream time remains as fallback and is fault-tolerant: bounded timeout, at most one in-flight refresh per track, and no corruption of previously persisted state on failure.
- **Failure reporting and metadata update APIs**: clients can report playback failures for a track (server records structured error state) and submit metadata corrections. The server sets state itself at file-scan and stream-refresh times; it never auto-clears `failing` on playback — skip-or-try is client behavior.
- **SQLite persistence with Flyway + Spring Data JPA**: all of the above is stored in a single SQLite database at `/config/gravifon.db` (default internal folder). The container declares `/music` and `/config` volumes and Compose uses Docker-managed `gravifon-library` and `gravifon-config` volumes by default. Operators can select host directories or named volumes with `GRAVIFON_LIBRARY_PATH` and `GRAVIFON_CONFIG_PATH`; application property locations remain configurable through `GRAVIFON_LIBRARY_DIR` and `GRAVIFON_CONFIG_DIR`. Schema is managed by Flyway migrations. This replaces JSON-file storage after sizing analysis: the target library of ~50k tracks makes per-playlist JSON rewrites impractical for routine metadata edits.

## Capabilities

### New Capabilities

- `track-registry`: the unified, persistent, metadata-bearing registry for all tracks — identity derivation, metadata model, duration, failure state, and scan reconciliation. Renames and redefines the current `media-library-catalog` capability.

### Modified Capabilities

- `playlist-management`: playlists become persistent, mutable, database-backed collections of shared track references; default all-tracks playlist requirement removed in favor of browsing + on-demand materialization; per-playlist playback mode; 501-read-only requirement removed.
- `playback-control`: playback context persisted in database keyed by session; per-playlist playback mode; PLAYING→PAUSED normalization on server restart and client init; position persisted with origin.
- `player-rest-api`: new playlist mutation endpoints, track metadata update endpoint, track failure-report endpoint; stream endpoint semantics extended to proxied stream tracks; error responses for expired/unresolvable streams.
- `audio-streaming`: source-aware resolution at `/api/stream/{trackId}`; server-side proxying of stream tracks; refresh-before-serve for expired stream URLs.
- `containerized-runtime`: `/music` and `/config` runtime volumes, Docker-managed fallback volumes, operator-selected host or named volume sources, and documented application path overrides.

## Impact

- **Code**: `catalog`, `playlist`, `playback`, and `api` packages substantially reworked — with explicit license to rename components to match the new architecture (`MediaCatalogService`/`catalog` → `TrackRegistry`/`registry`, `InMemoryPlaylistService` → `PlaylistService`); new repositories (Spring Data JPA), Flyway migrations, stream resolver SPI (list-in/list-out), no-op tag write-back handler, refresh scheduler.
- **APIs**: breaking changes to playlist and track resource shapes (clients receive full metadata + state per track); new mutation endpoints; playback state response gains session keying semantics (transparent, single `default` session for now).
- **Reference SPA**: existing static web assets are **removed** rather than migrated; the SPA will be rewritten from scratch against the new API.
- **Dependencies**: `spring-boot-starter-data-jpa`, Hibernate community SQLite dialect, `sqlite-jdbc`, Flyway (`flyway-core`), jaudiotagger for full tag reads, Jimfs (test-scoped, in-memory filesystem).
- **Deployment**: `/music` and `/config` are declared container volumes. Compose defaults to Docker-managed volumes and accepts `GRAVIFON_LIBRARY_PATH` and `GRAVIFON_CONFIG_PATH` for host or named volume sources. Without a persistent config source, the database remains ephemeral in the container writable layer. Runtime application paths can be overridden with `GRAVIFON_LIBRARY_DIR` and `GRAVIFON_CONFIG_DIR`.
- **Out of scope (Non-Goals)**: Bandcamp or any specific stream integration (later capability built on the resolver SPI); real tag write-back to files; metadata search/query endpoints; multi-session/multi-room playback; playlist import/export formats; SPA implementation.
